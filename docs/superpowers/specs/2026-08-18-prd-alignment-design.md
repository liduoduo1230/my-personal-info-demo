# 员工自助个人信息 PRD 对齐设计

## 目标与优先级

以《【员工自助】V1.2 个人信息》为本次 Demo 的最高业务依据，在保留当前员工端页面、员工端状态展示和 HR 审核抽屉结构的前提下，增量补齐字段、材料、审批规则和合同信息。此前与 PRD 冲突的约定以 PRD 为准。

## 页面模块与字段

首页继续按当前移动端单页展示，模块顺序保持为：个人基本信息、银行卡、证书信息、教育信息、工作履历、合同信息、家庭信息、紧急联系人。

个人基本信息首页仍作为一个模块展示。字段按业务规则独立响应点击，进入对应的修改表单：花名、手机号、个人邮箱、居住地址、政治面貌等进入个人信息表单；户口性质、户口地址、籍贯、婚姻状况、结婚日期、户口本本人页进入户口信息表单；姓名、性别、出生日期、身份证号、民族、身份证正面、身份证反面进入身份信息表单。页面不显示“三组”分组标题或额外分组卡片。

银行卡信息为单条需审批记录：开户银行、开户城市、银行卡号、开户支行、银行卡附件。页面保留发薪银行卡提示，开户名不作为表单字段。

证书信息保留“证书信息”名称，为多条需审批记录：获得日期、到期日、证书名称、证书类型、附件。永久有效时到期日允许使用“永久有效”。

教育信息为多条需审批记录：开始日期、结束日期、毕业学校、学历、专业、学历证书、学位证书、其他附件。

工作履历为多条需审批记录：开始日期、结束日期、公司名称、岗位、简历附件。

家庭信息为多条需审批记录：姓名、关系、联系方式、身份证号、附件。关系为子女时新增或修改必须提供出生证明等资料。

紧急联系人为单条无需审批记录：联系人姓名、联系方式。保存后立即生效，不进入 HR 审核列表；家庭成员转为紧急联系人仍沿用现有入口，但结果按 PRD 直接生效。

合同信息为多条仅查看记录：开始日期、结束日期、合同类型、附件。合同模块不提供编辑、新增、删除、保存、提交审核、撤回或任何点击跳转，不进入审核列表。

## 审批与生效规则

- 无需审批：个人信息组中的非身份/户口字段、紧急联系人；保存后直接更新可见数据。
- 需要审批：身份信息、户口信息、银行卡、证件、教育、工作履历、家庭信息，以及子女家庭记录的新增/修改/删除。
- 需审批申请提交后首页显示申请中的新数据；审核驳回恢复修改前数据；审核中的同一记录不可再次提交，撤回仅在申请详情页提供。
- 新增、修改、删除均作为整条申请进入 HR 审核；HR 端继续整单通过或退回。
- 直接生效的数据不创建审核请求，也不显示待审核状态。

## 数据兼容

- 在现有 `sections` 数据模型中新增 `contract` 记录集合，保留 `approvedData` 只读数据结构，不提供 `recordRequests`。
- 旧本地数据缺少新增字段或合同模块时，加载阶段与默认数据合并补齐，确保旧缓存不会造成空白页。
- 旧版 `certificate` 数据兼容读取，界面和审核模块继续使用“证书信息”文案，并补充附件字段映射。
- 重置 Demo 数据恢复完整 PRD 默认数据。

## 管理端影响

- 审核列表继续收集需审批模块；合同和紧急联系人不出现在列表中。
- 字段名称映射补齐 PRD 字段，证书模块显示“证书信息”。
- 现有详情抽屉继续展示新增、修改、删除标识、修改前数据、材料预览和整单操作。

## 验证范围

- 先增加失败测试：PRD 字段存在、合同多记录只读、紧急联系人直接生效、银行卡/教育/履历/证件字段和附件规则。
- 实现后运行 `node --check src/app.js`、`node --check src/domain.js`、完整 `node --test` 和 `git diff --check`。
- 通过 HTTP 访问员工端和管理端，确认页面返回 200 且员工端不会因旧缓存或合同数据缺失而空白。
